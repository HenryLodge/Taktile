# Audio, checksum phrases, and input

The device speaks only pre-recorded clips stored in its own flash. It never plays audio received from the host. All clips are generated once at build time with ElevenLabs (`tools/gen-audio.mjs`), which is also how ElevenLabs stays central to the project for the bounty.

## Checksum phrases

Each word comes from a 256-word list, so each word carries 8 bits.

```
tx phrase (3 words, 24 bits):      h = SHA256("TK-TX-v1"   || message_bytes);  words = W[h[0]], W[h[1]], W[h[2]]
address phrase (8 words, 64 bits): h = SHA256("TK-ADDR-v1" || wallet_pubkey);  words = W[h[0]] … W[h[7]]
```

The address phrase is longer because at enrollment the attacker chooses the address: 24 bits could be matched by brute-forcing keypairs against a known target address in minutes. The tx phrase is a secondary check (see `SECURITY_MODEL.md`), so 3 words is enough there.

- Tags are ASCII with no trailing NUL. `message_bytes` is the SIGN_REQUEST payload (the serialized Solana message). Word `i` is `W[hash byte i]`.
- `W` = the "even" list of the **PGP word list** (256 two-syllable words designed to be distinguishable when read aloud over a phone), by Patrick Juola and Philip Zimmermann (1995). No license is stated for the list; it is credited in the README. Source of truth: `tools/data/pgp-even-words.txt` (copied from magic-wormhole, MIT), spelling and capitalization as published. `node tools/gen-words.mjs` writes `core/src/tk_words.c` and `app/src/words.ts`. P1: alternate even/odd lists by position, as PGP intends, if flash space allows.
- `core/src/tk_checksum.c` (returns word indices; the device plays clips by index) and `app/src/checksum.ts` must produce identical output. Shared vectors: `tests/vectors/checksum.json` (generated by `tools/gen-vectors.mjs` with `node:crypto`), checked by `test_checksum` and `node --experimental-strip-types --test app/src/*.test.ts`.

## Clip inventory

| Group | Clips | Notes |
| --- | --- | --- |
| Checksum words | 256 | PGP even list |
| Digits and number words | `zero`–`nineteen`, `twenty`…`ninety`, `hundred`, `thousand`, `million`, `billion`, `trillion`, `point` | Amounts are read as numbers, e.g. "twelve point five" (see below) |
| Letters | `A`–`Z` | Spelling names and recovery words. Sent to text-to-speech as their spoken names ("ay", "bee", … "double you", "zee"): a bare "A" or "B" comes back as a sound ("ah", "buh"). The model guesses the language of such short input, so some names came out Spanish; those letters are regenerated individually and the one that sounds right is kept (`tts` overrides in `gen-clips.mjs`). An English-forced model (`eleven_turbo_v2_5`) was tried and sounded worse (2026-11-17) |
| Name punctuation | `space`, `hyphen`, `apostrophe` | Spelling contact names |
| Tokens | `USDC`, `SOL` | |
| Prompts | `send`, `to`, `unknown recipient do not sign`, `cannot sign this transaction`, `press confirm to sign or reject to cancel`, `checksum`, `address phrase`, `enter pin`, `pin digit number`, `starting at`, `wrong pin`, `attempts remaining`, `signed`, `cancelled`, `adding contact`, `remove`, `contact book full`, `already a contact`, `recovery word`, `repeat`, `speaker mode on`, `wallet wiped`; SETUP: `write down your recovery words`, `press OK for the next word, hold OK to repeat`, `hold OK to hear all words again, or press OK to finish`, `choose a new PIN`, `enter your PIN again`, `the PINs do not match`, `please wait`, `wallet created`; CONTACT_ADD: `press confirm to add or reject to cancel`, `contact added`; UNLOCK: `wallet unlocked`; voice commands: `your address phrase is`, `you have`, `contacts`, `wallet locked`; staking: `stake`, `with`, `unstake`, `stake account`, the pinned validator's name (`Kiln`, from `tools/validator.json`), `unknown validator, do not sign`; recovery word positions `twenty one`–`twenty four` (one clip each, so the number can't run into the letters that follow); and `speaker mode off` | Keep each prompt a separate clip; compose sentences by sequence |

**Amounts** (`core/src/tk_speech.c`) are read in tokens: SOL has 9 decimals, USDC 6. The whole part is read in English words without "and" ("one thousand two hundred five"); the digits after the point are read one by one with trailing zeros dropped (1,500,000 lamports → "zero point zero zero one five"). The largest u64 amount in USDC is about 18 trillion, hence the `trillion` clip.

**Recovery words** are spelled in full, letter by letter ("recovery word one, A, B, A, N, D, O, N"), so what the user writes down is the real BIP39 word that any wallet accepts. (Spelling only the first 4 letters, which identify every BIP39 word, was tried first and changed 2026-11-17: the prefixes don't look like words and most wallets want the whole word.) This avoids storing 2048 word clips. The letters are secret clips; the position number is public.

**Contact names** are at most 12 characters (`SERIAL_PROTOCOL.md`) and are spelled in full, character by character, using the letter, digit, `space`, `hyphen` and `apostrophe` clips, in P0. P1 option: a name clip recorded at enrollment and verified by the user through the earpiece, then stored on device (needs a protocol change — see `SERIAL_PROTOCOL.md` rules for changing the protocol).

## Format and storage

- Raw PCM, 16-bit signed LE, mono, 16 kHz, leading/trailing silence trimmed to 40 ms, peak-normalized to −3 dBFS.
- Stored as a **clip pack**: one flat image in the raw `clips` partition (10 MB, `firmware/partitions.csv`), no filesystem. `node tools/pack-clips.mjs` builds `tools/out/clips.bin` from `tools/out/clips/<id>.pcm`. Layout (little-endian): `"TKCP"`, u16 version 1, u16 count, u32 total length, u32 fingerprint, u32 CRC-32 of the clip data, then `count × {u32 offset, u32 len}`, then the PCM (each clip 4-byte aligned). Clip IDs are defined by core in `core/include/tk_clips.h`; `tools/clips.json` must match it.
- **Stale packs are refused.** The fingerprint is a CRC-32 over `"<id>:<text>\n"` for every clip; `tools/gen-clips.mjs` writes it to `core/include/tk_clips_fp.h` (`TK_CLIPS_FINGERPRINT`). At boot the device checks the header, every index entry, the clip count, the fingerprint and the data CRC (`core/src/tk_clippack.c`, bounds-checked and fuzzed). If any check fails, every clip is silent: a pack built for another clip list would speak the wrong word for an ID. `pack-clips.mjs` also refuses clips that were generated from older text (`tools/out/manifest.json`).
- Flash it once, and again whenever clips change: `parttool.py -p COMx --partition-table-file partitions.csv write_partition --partition-name clips --input ../tools/out/clips.bin` (from `firmware/`). `idf.py flash` doesn't touch it.
- Budget: ~0.6 s average × 32 KB/s ≈ 20 KB per clip; 369 clips = 7.94 MB of the 10 MB partition (2026-11-19). If space gets tight, switch to IMA ADPCM (4:1) before cutting clips.
- I2S output at 16 kHz; mono is duplicated to both channels (the UDA1334A plays both; the MAX98357A, with SD driven HIGH, plays the left). Gain (set by ear, `firmware/main/audio.c`): −9 dB with the earpiece alone, 50% (−6 dB) while the speaker is on (the bus is shared, so the earbuds get that level too).

## Generation (`tools/gen-audio.mjs`)

- **Clip list:** `tools/gen-clips.mjs` builds `tools/clips.json` (`[{id, name, text, say?}]`, one entry per ID in `core/include/tk_clips.h`, 369 clips) and `sim/src/clip_text.c`, so the simulator prints exactly what the device says. `text` is what the clip says; `say`, when present, is what is sent to text-to-speech instead (a pronunciation fix found by listening; e.g. "ess" for S); `tts`, when present, overrides generation settings for that clip (e.g. a seed that gave a letter the right pronunciation) and is part of its cache key. `--check` verifies both files.
- **Generation:** `tools/gen-audio.mjs` calls ElevenLabs `POST /v1/text-to-speech/{voice_id}?output_format=wav_16000` (API checked 2026-11-14). It asks for WAV rather than raw PCM so the sample format is read from the header (must be PCM 16-bit mono 16 kHz) instead of assumed; the header is then dropped. Voice ID and key come from `server/.env`; the key is never printed.
- **Fixed settings** so every clip sounds like one speaker (a few letters override the seed or text, see the clip inventory): `eleven_multilingual_v2`, `stability 0.75`, `similarity_boost 0.75`, `style 0`, `use_speaker_boost true`, `speed 0.95`, `seed 1`, `apply_text_normalization "off"`.
- **Processing:** trim leading/trailing audio below −45 dBFS down to 40 ms, peak-normalize to −3 dBFS.
- **Cache:** raw responses in `tools/out/cache/`, keyed by SHA-256 of (spoken text, voice, every setting), so reruns only pay for changed clips. `--dry-run` shows what would be generated; `--only <ids|names|text>` regenerates a few; `--force` ignores the cache.
- **Outputs** (gitignored): `tools/out/clips/<id>.pcm` (packed into `tools/out/clips.bin` by `pack-clips.mjs`), `tools/out/preview/<id>-<text>.wav` (listen to these), `tools/out/manifest.json`. First full run: 342 clips, 2,303 characters, 333 ms–2.4 s each, 227 s and 6.94 MB in total (budget 10 MB). The 9 SETUP / speaker-off prompts added 2026-11-17 (227 characters); then the 26 letters re-recorded from their names, "pin digit number", "starting at" and "twenty one"–"twenty four" (146 characters); then 10 letters picked by listening from 42 candidates (an English-forced model was tried and rejected): 356 clips, 246.1 s, 7.51 MB; then the 2 CONTACT_ADD prompts (2026-11-18): 358 clips; then `wallet unlocked` (2026-11-18): 359 clips; then the 4 voice-command prompts (2026-11-19, 51 characters): 363 clips, 254.3 s, 7.76 MB; then the 6 staking prompts (2026-11-19, 63 characters): 369 clips, 260.1 s, 7.94 MB.
- **Listen to every preview before packing**: what the device says is trusted output. Fix a bad clip with a `say` override in `gen-clips.mjs`, rerun `gen-clips`, then `gen-audio` (only that clip is regenerated), then `pack-clips` and reflash the pack.

## Output routing

Core marks each clip it plays as public or secret (`play_clip(..., secret)`): the three checksum words, every PIN digit value and every recovery-word letter are secret; prompts, amounts, tokens, spelled names, the 8 address-phrase words and PIN positions ("pin digit number three, starting at") are public. (The address phrase comes from a public address and is read over the phone, SECURITY_MODEL.md.)
- **Earpiece (UDA1334A) is the default** and the only path for secret clips: checksum words, PIN digit values, and recovery words.
- **The speaker is off unless speaker mode is on.** The MAX98357A's SD pin (`SPK_EN`) is driven LOW at boot, before I2S starts, and stays LOW except while a clip plays in speaker mode. Firmware's `play_clip` sets the routing before each clip's first sample and drains the I2S buffers after every clip. With speaker mode off, nothing reaches the speaker.
- **Speaker (MAX98357A) "demo mode"** is toggled only on the device: hold OK + BACK together for 3 s while the device is idle (between requests; `core/src/tk_chord.c`, `firmware/main/buttons.c`, `main.c`). A double pulse, then "speaker mode on" (already on the speaker) or "speaker mode off" (still on the speaker, then it goes off). **Idle only:** during a flow the chord does nothing (holding OK there means repeat), so routing never changes mid-sentence. Only a reboot resets it; reconnecting USB does not (decided 2026-11-18). The host can neither enable it nor see it (no protocol field). While it is on, **every clip plays on the speaker too, secret ones included** (PIN digit values, checksum words, recovery-word letters), so the audience hears exactly what the earbuds hear (changed 2026-11-20 for the demo; before, secret clips stayed in the earpiece and SETUP was refused in this mode). The earbuds get the louder speaker level too (shared bus). Anyone in the room hears the PIN digits, so turn it off after the demo.

## Buttons

| Button | Physical | Use |
| --- | --- | --- |
| UP / DOWN | Small, in a row | Change digit during PIN entry; scroll |
| OK | Small | Commit digit; long-press 2 s = repeat last announcement |
| BACK | Small | Delete previous digit |
| CONFIRM | Large round cap, right side | Approve signing |
| REJECT | Large square cap, left side | Reject; long-press 2 s = cancel current flow |

Debounce 30 ms (scanned every 5 ms). UP, DOWN, BACK and CONFIRM count on press; OK and REJECT count on release if held under 2 s, or as a long press the moment the hold reaches 2 s.

**Every press that starts during a clip is discarded**, including long presses of OK and REJECT, and a button still held when a clip ends is ignored until it is released. This is what makes I6 hold (CONFIRM pressed during the announcement never counts); `core/include/tk_platform.h` (`wait_button`) is the contract, and the simulator does the same. To repeat or cancel, press after the clip ends.

## PIN entry ("rotary" scheme)

For each of the 6 digits:

1. Device picks a random start digit (hardware RNG) and announces "pin digit number *three*, starting at *seven*": the position and "starting at" are public, the start digit is a secret clip.
2. UP / DOWN step the digit (wrapping 0–9); the device speaks each new value.
3. OK commits; BACK goes back one digit.

An observer sees only up/down counts, which reveal nothing without the private start digit. Each press gives a short haptic tick so the user knows it registered.

When signing (or adding a contact) needs the PIN: "enter pin", the six digits as above, then "please wait" during the 2.6 s check. A wrong PIN: three pulses, "wrong pin, *n* attempts remaining", and entry starts again; the tenth wrong PIN in a row: "wallet wiped" (SECURITY_MODEL I7). The PIN is needed again after every signature.

**Unlocking** (`UNLOCK`, `core/src/tk_flow.c`): the app asks for the PIN *before* it builds the transaction, so the blockhash is fresh when the device signs. The same PIN entry as above, then a double pulse and "wallet unlocked". The next `SIGN_REQUEST` skips PIN entry: the announcement, then "press confirm to sign or reject to cancel". Already unlocked: nothing is played.

**Adding a contact** (`CONTACT_ADD`, `core/src/tk_enroll.c`): "adding contact", the name spelled ("A, L, I, C, E"), "address phrase" and its 8 words. The user calls the contact, who reads the phrase for the same address from their own wallet tool; they must match word for word. If locked, PIN entry follows. Then "press confirm to add or reject to cancel": CONFIRM stores it (double pulse, "contact added"); REJECT or 30 s without a press cancels; **hold OK repeats the whole announcement** and restarts the 30 s, as often as needed during the call. A contact book that is full ("contact book full") or already has that name or address ("already a contact") is refused at once with a warning pulse. Adding a contact does not end an unlocked session.

**Voice commands** (`SPEAK_ADDRESS`, `SPEAK_CONTACTS`, `LOCK`, `core/src/tk_flow.c`; the app sends them for "what is my address", "who are my contacts", "lock"). If locked, the two SPEAK commands start with PIN entry as above (no "wallet unlocked": the answer follows). "What is my address": "your address phrase is" and the device's own 8 words, public clips (the same phrase CONTACT_ADD reads for a contact, computed from the device's public key). "Who are my contacts": "you have *n* contacts", then "one", the first name spelled, "two", the second, and so on. "Lock": "wallet locked", even if it was already locked. A host CANCEL or long REJECT stops the answer between clips. These answers are the trusted ones: the laptop's own answers (balance, activity, staked) are app speech from untrusted RPC data (SECURITY_MODEL "Command sources").

**Staking** (`SIGN_REQUEST` Shapes C and D, SOLANA.md). Stake: "stake *amount* SOL with Kiln, stake account *n*, checksum *w1 w2 w3*" (the amount is everything moved into the stake account, including the 0.00166624 SOL rent reserve, so "stake 1 SOL" is announced as "one point zero zero one six six six two four"); unstake: "unstake, stake account *n*, checksum *w1 w2 w3*". *n* is the account number 0–15 the device recomputed itself; the validator name is the pinned one (any other vote account is refused before anything is announced: three pulses, "unknown validator, do not sign"). Then PIN if locked and the same confirm window as a send: hold OK repeats, CONFIRM signs. Only the checksum words are secret.

## SETUP (`core/src/tk_setup.c`)

The host sends `SETUP`; everything else happens on the device. Refused at once and silently with `WALLET_EXISTS` while a wallet exists (I10); refused with `DEVICE_ERROR` without working audio or in speaker mode (recovery words are never offered there).

1. **PIN first**: "choose a new PIN", rotary entry as below; "enter your PIN again", entry again. If they differ: three pulses, "the PINs do not match", start over; after 3 mismatches SETUP is cancelled. The press timing of both entries is mixed into the entropy (SECURITY_MODEL I11), which is why the PIN comes first.
2. "please wait" while the words are generated (about 0.5 s).
3. "write down your recovery words", then each of the 24 words: "recovery word *n*, *letters*" (positions 21–24 are single "twenty one"… clips). After word one: "press OK for the next word, hold OK to repeat". **OK** = next word (tick), **long OK** = repeat this word, **BACK** = previous word, **REJECT** = stop (`REJECTED_BY_USER`), **long REJECT** = cancel. Up to 5 minutes per word, then it cancels.
4. After word 24: "hold OK to hear all words again, or press OK to finish". Long OK starts again at word one; BACK returns to word 24.
5. OK: "please wait" (the PIN key derivation, about 2.6 s), then "wallet created" and a double pulse. The device is unlocked as after a PIN: until the next signature, 5 minutes, the USB host going away, or a reboot (SECURITY_MODEL I7).

Nothing is stored until step 5, so cancelling, a timeout or unplugging at any earlier point leaves no wallet. The P0 flow only asks the user to acknowledge each word; it does not quiz them on the words.

## Haptic patterns (DRV2605L, ERM effect library A)

| Pattern | Meaning | Sequence (`firmware/main/haptics.c`, tuned by feel 2026-11-17) |
| --- | --- | --- |
| Single short tick | Button press registered | Effect 1 (Strong Click) |
| Double pulse | Signed successfully | Effect 1, 100 ms pause, effect 1 twice back to back (a longer second pulse is easier to feel than library effect 10, Double Click) |
| Long buzz | Rejected or cancelled | Effect 15 (750 ms Alert) |
| Three strong pulses | Warning: unknown recipient, wrong PIN, cannot sign | Effect 14 (Strong Buzz) three times, 150 ms apart |

Playback is fire-and-forget: firmware loads the chip's sequencer and returns, so the next clip starts at once; a new pattern replaces one still playing. If the DRV2605L is missing, haptics are off and everything else works: haptics are feedback, not a security control, and every warning is also spoken.
